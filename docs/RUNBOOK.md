# Эксплуатация на NAS (UGREEN DXP4800 Plus)

> **Статус проверки.** Конфигурация Docker/Cloudflare подготовлена и проверена всем, что возможно без самого NAS
> (см. «Что проверено и что нет» в конце). **Первый запуск на NAS нужно пройти по чек-листу ниже** — он закрывает остаточные риски.

## 1. Архитектура развёртывания

```
Интернет ──HTTPS──> Cloudflare (Access, WAF) ──туннель (исходящий)──> cloudflared ─┐
                                                                                   ▼
                  сеть app:   cloudflared ──> web (Next.js :3000) ──/api──> api (NestJS :4000) ── worker
                  сеть db (internal, без выхода в интернет):  api, worker, backup ──> postgres
```
Порты postgres/api/web на хост **не публикуются**. База данных находится в сети `db` с `internal: true` — у неё нет ни входящих, ни исходящих соединений с интернетом.
Контейнеры приложения: пользователь `node`, `cap_drop: ALL`, `no-new-privileges`. Адрес API для web **зашивается в образ при сборке** (`http://api:4000`, build arg) — менять имя сервиса `api` в Compose нельзя без пересборки.

## 2. Первый запуск

1. Docker на NAS (UGOS → «Docker»). Скопируйте репозиторий (`git clone`).
2. `cp .env.example .env && chmod 600 .env` и заполните:
   - `POSTGRES_PASSWORD` — `openssl rand -hex 16` (только латиница/цифры/`_`/`-`: пароль подставляется в URL подключения);
   - `INITIAL_ADMIN_EMAIL` / `INITIAL_ADMIN_PASSWORD` (≥ 12 символов, буквы и цифры) — только для первого входа;
   - `CLOUDFLARE_TUNNEL_TOKEN` (п. 3);
   - `BACKUP_DIR` — **абсолютный путь на другом томе/диске**, чем база данных (например `/volume2/backups/procurement`).
3. Cloudflare Zero Trust → Networks → Tunnels → создать туннель; Public hostname → `http://web:3000`; скопируйте токен в `.env`.
4. **Cloudflare Access** (обязательно): Access → Applications → Self-hosted для вашего домена; политика — только ваши сотрудники (почта/SSO + OTP). Это дополнительный слой перед страницей входа приложения.
5. **WAF/Rate limiting** (рекомендуется): правило «Rate limiting» на `/api/auth/login` (например 10 запросов/мин на IP) — поверх лимитов самого приложения.
6. `./deploy/preflight.sh` — должен завершиться без ошибок.
7. `docker compose up -d --build` (первая сборка 5–10 минут).
8. `docker compose ps` — `api`, `web`, `postgres` в состоянии `healthy`; `docker compose logs api | tail` — «Nest application successfully started».
9. Откройте домен → вход начальным администратором → **обязательная смена пароля** → создайте пользователей (встроенные роли: FINANCE подтверждает платежи, MANAGER ведёт справочники, VIEWER — просмотр; свои роли с произвольным набором прав создаёт SUPER_ADMIN в разделе «Роли и права»).
10. **Удалите `INITIAL_ADMIN_PASSWORD` из `.env`** и `docker compose up -d` (страница «Система» напоминает, пока он задан).
11. Страница **Система** (меню администратора): все проверки «OK» (допустимые предупреждения: «Курсы валют» до первого подтверждения; «Снимки» до открытия дашборда).
12. Подтвердите курсы валют (раздел «Курсы валют») — без них итоги в USD неполные.

### Чек-лист первого запуска на NAS (закрывает непроверенное)
- [ ] Образы собрались (`docker compose build` без ошибок); `docker compose ps` — все сервисы healthy.
- [ ] Вход через **HTTPS-домен** работает; cookie имеет префикс `__Host-` (DevTools → Application → Cookies).
- [ ] Загрузка реального файла: Импорт → проверка → сохранение; итоги совпали с таблицей.
- [ ] `docker compose logs backup` — «backup ok» и «restore-test ok»; в Системе: «Резервные копии» и «Проверка восстановления» — OK.
- [ ] Перезагрузка NAS → через 2–3 минуты `docker compose ps` — всё поднялось само.
- [ ] Страница Система: «Фоновый воркер» — OK, «Прокси (IP клиента)» — OK; в аудите (`/api/audit`) IP входа — ваш реальный, а не адрес контейнера.
- [ ] Ручной тест PDF/Excel-выгрузки из браузера.

## 3. Ежедневная эксплуатация
- **Состояние:** страница «Система»; внешний мониторинг — Uptime Kuma на `https://<домен>/api/health` (200 — база доступна, 503 — нет). Через Cloudflare Access для робота создайте Service Token.
- **Логи:** `docker compose logs -f api` — одна JSON-строка на запрос (метод, путь без query, статус, мс, пользователь, IP, `x-request-id`); тела запросов, cookie и пароли не пишутся. Ротация 10 МБ × 5 на сервис.
- **Пользователи:** увольнение — «Отключить» (сессии аннулируются сразу). Роли — наименьшие необходимые.
- **Ежемесячно:** смотреть аудит (вход, ошибки входа, экспорт, изменения прав), проверять место на диске (Система).

## 4. Резервное копирование и восстановление

**Что копируется:** сервис `backup` сразу при запуске и далее раз в сутки делает `pg_dump -Fc` (+ контрольная сумма `.sha256`) и архив загруженных файлов в `BACKUP_DIR`. Копия попадает в каталог только после проверки читаемости; хранится 30 дней, но **не менее 7 последних** (`BACKUP_KEEP_DAYS`).
**Проверка восстановления:** после первой копии и затем раз в неделю `restore-test.sh` восстанавливает последнюю копию в **отдельную** БД `pf_restore_test`, проверяет контрольную сумму, миграции, инварианты данных (подтверждённые платежи имеют сумму, суммы неотрицательны), наличие триггеров защиты (неизменяемость аудита и платежей), сравнивает аудит с рабочей БД и удаляет временную БД. Результат — `last-restore-test.json`, виден в «Системе»; при сбое статус «Проблема».
Вручную: `docker compose run --rm backup /backup.sh`, `docker compose run --rm backup /restore-test.sh`.

**Копии вне NAS (обязательно!):** копия на том же NAS не защищает от кражи, пожара или отказа NAS. Настройте синхронизацию `BACKUP_DIR` в облако или на второй носитель (UGOS: Синхронизация/Резервное копирование). Раз в квартал восстанавливайте копию **на другом компьютере**.

### Восстановление после аварии
```sh
docker compose stop api worker web                       # остановить приложение (postgres и backup остаются)
docker compose exec -T postgres psql -U pf -d postgres -c 'DROP DATABASE pf' -c 'CREATE DATABASE pf'
docker compose exec -T postgres pg_restore -U pf -d pf --no-owner < /путь/BACKUP_DIR/pf-YYYYMMDD-HHMMSS.dump
tar xzf /путь/BACKUP_DIR/uploads-YYYYMMDD-HHMMSS.tgz -C <каталог тома uploads>     # при потере загруженных файлов
docker compose start api worker web
```
Проверка: вход работает; число договоров/платежей соответствует ожидаемому; «Система» — все проверки OK; в аудите нет «разрыва» после момента копии (всё, что сделано после копии, придётся повторить).
Полная потеря NAS: новая установка по разделу 2 → восстановление БД и `uploads` из внешней копии → `TOKEN_ENCRYPTION_KEY` из прежнего `.env` (иначе токены Google придётся подключить заново).

## 5. Обновление и откат
`./deploy/update.sh` — проверка окружения → резервная копия → `git pull --ff-only` → сборка → запуск → ожидание healthy.
**Откат** (миграции БД только «вперёд»):
1. Если обновление **не меняло схему БД**: `git checkout <предыдущий тег/коммит> && docker compose up -d --build`.
2. Если менялась схема: восстановите БД из копии, сделанной `update.sh` перед обновлением (раздел 4), затем п. 1. Данные, введённые после обновления, будут потеряны — поэтому обновляйтесь вне рабочего времени.

## 6. Безопасность в эксплуатации
Подробно — `docs/SECURITY.md`. Коротко: Cloudflare Access перед приложением; HTTPS только на стороне Cloudflare; cookie `__Host-` + HttpOnly + SameSite=Lax; CSRF-токен на изменяющих запросах; пароли — Argon2id; блокировка после 5 неудачных входов, лимит запросов; права проверяются на сервере; журнал аудита неизменяем (триггер БД); подтверждённые платежи неизменяемы (триггер БД).
**Секреты** только в `.env` (права 600, не в Git). Ротация: пароль БД — смена в `.env` + `ALTER USER pf PASSWORD ...` + перезапуск; `TOKEN_ENCRYPTION_KEY` — смена делает сохранённые токены Google нечитаемыми (подключить аккаунт заново).

## 7. Google Sheets
**Публичная таблица** (настройки не нужны): «Настройки доступа → Все, у кого есть ссылка → Читатель». В приложении: «Google Sheets» → ссылка → «Проверить доступ» → лист и год плана → «Подключить и загрузить данные».
**Закрытая таблица** (OAuth, права только на чтение таблиц `spreadsheets.readonly`):
1. Google Cloud Console → проект → включить **Google Sheets API**.
2. OAuth consent screen (External; в режиме Testing добавьте свой аккаунт в Test users) → Credentials → **OAuth client ID → Web application**.
3. Authorized redirect URI: `https://<домен>/api/google/oauth/callback`.
4. В `.env`: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` (https), `TOKEN_ENCRYPTION_KEY` (`openssl rand -base64 48`); `docker compose up -d`.
5. «Google Sheets» → «Подключить Google-аккаунт» → разрешить доступ.
Синхронизация только **читает** таблицу и готовит предпросмотр изменений (воркер проверяет каждые 5 минут); договоры и оплаты меняются только после подтверждения. Refresh-токены хранятся в БД зашифрованными (AES-256-GCM). Отзыв доступа: myaccount.google.com → Безопасность → Сторонние приложения.

## 8. Диагностика
| Симптом | Что смотреть |
|---|---|
| Сайт не открывается | `docker compose ps`; `docker compose logs cloudflared` (туннель), `web`, `api` |
| 502/«Bad gateway» | api не healthy: `docker compose logs api` (миграции, подключение к БД) |
| Вход «Недействительный CSRF» / выкидывает | часы NAS сильно расходятся; cookie блокируется — проверьте, что открыт именно HTTPS-домен |
| Все пользователи «с одного IP», лимиты срабатывают у всех | `TRUST_PROXY_HOPS` должен быть 2 (Cloudflare → web → api) |
| В Системе «Фоновый воркер: нет сигналов» | `docker compose logs worker`; `docker compose restart worker` |
| В Системе «Резервные копии: копий нет/устарели» | `docker compose logs backup`; свободное место; права на `BACKUP_DIR` |
| Google: «Таблица закрыта» | доступ «по ссылке» или подключите аккаунт (раздел 7) |
| PDF без кириллицы | образ api собран без зависимости `dejavu-fonts-ttf` — пересоберите (`docker compose build api`) |

## 9. Что проверено и что нет
**Проверено автоматически:** 147 интеграционных тестов API на настоящей PostgreSQL (в т.ч. безопасность: заголовки, cookie, прокси, лимиты, SQL-инъекции, XSS, размеры запросов, права), 69 тестов финансового ядра и импорта, 21 E2E-сценарий в браузере на web, собранном и запущенном как в Docker-образе (standalone), 38 тестов скриптов развёртывания (резервное копирование, проверка восстановления, preflight) с заглушками PostgreSQL-утилит; запуск приложения из урезанного дерева зависимостей (`npm prune --omit=dev`: миграции → API → воркер → PDF); валидность `docker compose config`.
**Проверено на NAS UGREEN (Docker 29, Compose v5):** сборка образов api/web/worker; запуск postgres+api+worker+web (healthy), применение 8 миграций; создание данных через API (долг договора совпал с расчётом); **реальные `pg_dump -Fc` и `pg_restore` в контейнере `backup`**: копия + контрольная сумма, восстановление в `pf_restore_test`, инварианты и триггеры, страница «Система» показывает копию и проверку восстановления как OK. Найдено и исправлено: пустые `GOOGLE_*` из Compose ронял API при старте; `last-restore-test.json` создавался с правами 700 (root) и API не мог его прочитать.
**Не проверено:** cloudflared и доступ через настоящий HTTPS-домен (CSP/HSTS в браузере, cookie `__Host-` в браузере); перезагрузка NAS; недельный автозапуск проверки восстановления по расписанию (запускался вручную).
